# Architecture Decision Records (ADR)

## ADR-001: GitHub API 作为数据层（无外部数据库）

- **状态**: 已采纳 (2026-05-20)
- **背景**: 需要一个零成本、零运维的数据存储方案
- **决策**: 使用GitHub仓库存储JSON数据文件，通过GitHub API读取 + jsDelivr CDN缓存
- **原因**: 
  - 免费且稳定，GitHub Pages自带CDN
  - JSON文件版本化，天然支持数据追溯
  - 无需数据库运维，纯静态站点
- **代价**: 
  - 写入操作需GitHub Token，受API速率限制
  - 大文件加载慢（videos 820条≈4MB）
  - 无实时数据推送能力
- **替代方案**: Firebase（需Google账号+付费）、Supabase（免费额度有限）、SQLite+服务端（需服务器）

## ADR-002: 暗色主题为默认

- **状态**: 已采纳 (2026-05-21)
- **决策**: 暗色主题为默认，亮色主题可选覆盖
- **原因**: 金融研究工具用户长时间盯屏，暗色减少视觉疲劳；同花顺/iFinD等专业终端均默认暗色
- **实现**: `:root,[data-theme="dark"]` 作为根选择器，`[data-theme="light"]` 覆盖变量

## ADR-003: ES Module 模块化（无全局变量）

- **状态**: 已采纳 (2026-05-21)
- **背景**: 旧版6个JS文件全部L3+L4混合，用全局变量通信
- **决策**: 全部使用 import/export ES Module，`<script type="module">`
- **原因**: 强制模块边界、防止跨层调用、消除全局变量污染
- **代价**: 需要浏览器支持ES Module（IE不支持，但目标用户用Chrome）

## ADR-004: 架构蓝图驱动开发

- **状态**: 已采纳 (2026-05-21)
- **决策**: 所有代码必须先对应蓝图层级和模块，蓝图版本化迭代
- **原因**: 防止"代码先行、架构滞后"的技术债务积累
- **规则**: 任何代码改动必须先回答"对应蓝图哪一层哪个模块"

## ADR-005: 系统ID(_id)与外部ID(source_id)严格分离

- **状态**: 已采纳 (2026-05-20)
- **决策**: 系统内部只用_id关联，source_id(BV号等)仅作业务字段
- **原因**: 外部ID可能变化或重复，系统ID必须稳定且全局唯一
- **实现**: _id格式 `{类型前缀}_{随机8位hex}`，如 up_3d80ddbb83fd

## ADR-006: 数据层只存原始数据，逻辑层实时计算

- **状态**: 已采纳 (2026-05-21)
- **决策**: JSON文件只存原始记录，统计/聚合/排序在显示时由逻辑层实时计算
- **原因**: 避免数据冗余和不一致，简化写入逻辑
- **代价**: 每次渲染需重新计算，大数据量时需缓存优化

## ADR-007: 密码模块在head中隔离

- **状态**: 已采纳 (2026-05-21)
- **背景**: 旧版密码JS与业务JS耦合，排在4.8MB数据后面导致间歇性失效
- **决策**: 密码验证逻辑放在 `<head>` 的独立 `<script>` 中，不依赖任何外部JS
- **原因**: 关键模块必须隔离，不能被业务代码阻塞

## ADR-008: CST时区用于所有日期处理

- **状态**: 已采纳 (2026-05-22)
- **背景**: B站视频发布日期因UTC/CST时区差导致约5%的日期错误
- **决策**: 所有涉及日期的代码必须使用CST(UTC+8)时区
- **实现**: `datetime.fromtimestamp(ts, tz=timezone(timedelta(hours=8)))`
- **教训**: B站API返回的pubdate是UTC时间戳，转日期时必须指定CST时区
